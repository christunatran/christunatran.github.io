Technical Plan: Modern Đèn Kéo Quân

A series of experiments to build the core loop, one piece at a time, in an order that teaches the concepts along the way. Each experiment ends with a number that was measured and a decision. Speech, translation and images each work on their own first, then get chained together.

Core loop: Vietnamese speech → transcription (Moonshine) → English translation and image subject (Gemma) → black-and-white silhouette (Stable Diffusion + silhouette gate) → six-slot procession on six LCD panels behind paper.

Constraints: 100% local and offline on a Raspberry Pi 5 (8 GB). Backlight layer fixed and set by me; the AI only changes the silhouette layer. Rotation is animated, not mechanical.

How to learn throughout

  • Keep a lab notebook from day one. A git repo with one markdown entry per experiment: what I’m testing, setup, the numbers, what surprised me, what I decided. It’s how I’ll actually learn, and by the end of the year it’s my thesis documentation. (Template at the bottom of this file.)
  • Change one thing at a time. When something breaks or gets slower, I’ll know why.
  • Measure the same four things every time: speed, peak memory, temperature and quality.

A two-minute primer on local AI

  • A model is a large file of learned numbers (weights). On its own it does nothing.
  • A runtime is the program that runs the model. Three will come up:
    • Ollama, the easiest way to run text LLMs (built on llama.cpp)
    • LiteRT-LM, what the Gemma Translator uses
    • PyTorch, what runs Stable Diffusion
  • Quantization stores the weights with fewer bits, often 4 instead of 16. That shrinks memory use and speeds things up at a small cost in quality. It’s the main reason LLMs fit on a Pi at all.
  • Tokens are word pieces. LLM speed is measured in tokens per second.
  • Temperature controls randomness. Keep it low for translation, since I want the same answer every time.
  • On a Pi, everything runs on the CPU and is limited by memory. Small models (around 1–2 billion parameters) are realistic; big ones aren’t.

Phase 1: Foundations (about 1 week)

E1. Finish the base setup

  • Run the thermal test: 
    sudo apt install -y stress-ng
stress-ng --cpu 4 --timeout 300s &
    Check vcgencmd measure_temp every minute or so while it runs.
  • Pass: vcgencmd get_throttled reads throttled=0x0 after 5 minutes at full load.

E2. Set up a real workflow

  • Install the Remote-SSH extension in VS Code on the laptop, so files on the Pi can be edited as if they were local.
  • Create a project folder with a Python virtual environment and a git repo.
  • I’ll learn: basic Linux, virtual environments, git.
  • Pass: I can edit a script on the Pi from VS Code and run it.

Phase 2: First local LLM (2–3 weeks)

E3. Hello LLM with Ollama

The gentlest on-ramp.

curl -fsSL https://ollama.com/install.sh | sh
ollama run gemma3:1b --verbose
  • Use whichever small Gemma model Ollama currently lists; gemma3:1b is an example name. The model downloads once and runs offline after that.
  • Chat with it, then read the “eval rate” that --verbose prints: that’s tokens per second.
  • Watch memory in a second SSH window with htop.
  • I’ll learn: model files, quantization, tokens per second, prompts.
  • Measure: tokens/second and memory for a 1B model, then a larger one, to get a feel for the trade-off.

E4. Gemma E2B through LiteRT-LM (the production path)

  • Set it up following the Gemma Translator repo, but run only its backend pieces by hand. Its full deploy script turns the Pi into a kiosk, which I don’t want on the development Pi yet.
  • Measure: speed and memory, compared with Ollama.
  • Decision: which runtime to use.

E5. Translation quality

  • Build a test set of about 20 Vietnamese sentences, ideally from real people, with different speakers and topics.
  • Test two prompts:
    1. a plain translation
    2. “translate, then give a short visual subject for one silhouette”
  • Ask the model to answer in a fixed format, for example {"english": "...", "subject": "..."}. My code checks the format and retries if it’s broken.
  • I’ll learn: prompt design and handling unreliable model output (the same mindset as the silhouette gate).
  • Measure: meaning preserved (out of 20), format success rate, seconds per sentence.

Phase 3: Speech (about 2 weeks)

First purchase: a USB microphone.

E6. Moonshine Vietnamese on the Pi

  • First confirm Vietnamese is supported in the current Moonshine release.
  • Record with arecord, transcribe, and compare against what was actually said, using the same speakers and sentences as E5.
  • If Moonshine is weak, test whisper.cpp as a fallback.
  • I’ll learn: speech-model basics, audio recording on Linux, word error rate (the standard accuracy measure: the share of words wrong).
  • Measure: accuracy and seconds per sentence.

E7. First mini-loop: speak → text → translation

  • Measure: total time from speech to English.

Phase 4: Images (3–4 weeks)

E8. Silhouettes on the laptop first

Iterating there is much faster.

  • Run SDXL-Turbo with a prompt test set through silhouette_pipeline.py.
  • I’ll learn: diffusion basics (steps, seeds, resolution, why guidance 0 disables negative prompts).
  • Measure: how many images pass the gate, and whether the silhouettes read through paper held over the screen.

E9. SDXL-Turbo on the Pi

  • Raise swap to 8 GB.
  • Install CPU-only PyTorch in a virtual environment.
  • Run the timing script, measuring:
    • load time and generation time (separately)
    • peak memory (/usr/bin/time -v shows it as “Maximum resident set size”)
    • swap written (grep pswpout /proc/vmstat before and after; the difference × 4 KB)
  • Do 10 runs back to back, watching temperature.
  • If it’s too slow or swaps heavily, compare SD-Turbo (a smaller sibling model), SD 1.5 and OnnxStream.
  • Check each model’s license on its model card. Some Stability AI models restrict commercial use, which matters if this ever becomes a product.
  • Decision: which image model, and whether an NVMe drive is needed.

E10. Gate on the Pi

  • Pass: a typed subject goes in, a silhouette lands in the archive.

Phase 5: The full core loop (about 3 weeks)

E11. Memory choreography

  • Decide which models stay loaded and which get unloaded between steps.
  • Measure: peak memory for each strategy, and make sure nothing gets killed for running out of memory.

E12. Core loop on the Pi, viewed from the laptop

  • Speak, and the silhouette goes into the archive.
  • Serve the p5 sketch from the Pi and open http://tunapee.local:8000 in the laptop’s browser. That shows the display with no monitor attached (the local network is used for viewing only).
  • Measure: speech-to-silhouette time, over 20 cycles.

E13. Make it robust

  • Run generation and display as two separate programs that start automatically at boot (using systemd, Linux’s service manager).
  • Tests:
    • kill the generator and check that the display keeps glowing
    • pull the power and check that the archive survives
  • Port the display to pygame here, if I decide to.

Phase 6: Real display hardware (after Phase 5)

  1. Buy one panel and run the 1080p test (set the Pi’s output to 1920×1080; if the panel shows a scaled picture, it will work with the controller).
  2. Add the video wall controller and run all six panels.
  3. Attach the playback button (GPIO 17 to ground).

Big decision points

AfterDecide
E5Which LLM runtime, which translation prompt
E6Which speech model
E9Which image model, NVMe or not, how long generation takes (shapes the experience design)
E12Whether the core loop is fast and stable enough to start buying display hardware

Timing: roughly 3 months to a working core loop if things go reasonably well. That leaves most of the year for the parts that make it a thesis: testing with people, the lantern’s form and light, and the concept.
